# D-088 Lookup by key id, then a constant-time compare, with a dummy compare when the id is unknown

- **Decision:** Settles PLAN.md M14's lookup. For a well-formed key, the gateway reads the row for its key id: `SELECT key_id, tenant_id, key_hash, revoked_at IS NOT NULL AS revoked FROM api_keys WHERE key_id = $1`, a primary-key lookup, parameterized. Then it always computes `hash_key` of the presented key and compares it with `hmac.compare_digest` against the row's hash or, when there is no row, against a fixed 32-byte dummy. It accepts the key only if a row exists, the digests are equal and the row is not revoked. Revocation is checked after the compare, so a revoked key and a wrong secret do the same work. A malformed key is rejected before any lookup or hash.
- **Why:** CLAUDE.md asks for a constant-time compare. Comparing in the gateway with `compare_digest` is that, whatever Postgres does. The dummy compare means an unknown id costs the same hashing and comparing as a known one with a wrong secret. What timing can still show is whether a key id exists (an index hit and a row versus none) and whether a key was well formed (no lookup at all). Neither is secret: the format is public (D-086), and an id grants nothing without its secret.
- **Alternatives:** Look the key up by its hash, `WHERE key_hash = $1` (common and works: the attacker controls only the input to SHA-256, so the B-tree's non-constant compare of digests leaks nothing usable; but the compare is then Postgres', not the gateway's, and there is no id for logs or revocation); compare the hex strings with `==` (leaks the length of the matching prefix); skip the dummy compare (an unknown id would answer measurably faster than a wrong secret).
- **Risk:** The dummy compare equalizes the gateway's work, not the database's; the difference that remains is on the id, as above. D-090's cache makes that difference much larger and easier to measure: an id whose row is cached answers from memory, while an unknown id always costs a Postgres round trip. It still shows only whether an id exists (and was used recently), never anything about a secret, so it is accepted on D-086's ground that ids are public.
- **Revisit when:** The key format changes, or keys get scopes that make an id sensitive.

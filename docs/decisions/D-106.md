# D-106 Redis down or slow: the limiter fails open after 250 ms; unlike auth, which fails closed

- **Decision:** Settles PLAN.md M16's "behavior when Redis is down".
  - **The client:** `Redis(connection_pool=BlockingConnectionPool.from_url(url, max_connections=50, timeout=0.25, socket_timeout=0.25, socket_connect_timeout=0.25, retry=Retry(NoBackoff(), 0)))`, closed with `aclose(close_connection_pool=True)`. Read in redis-py 8.1.0's source: the plain `Redis()` constructor defaults to retries with exponential backoff, and the default asyncio pool raises `MaxConnectionsError` at once past 100 connections in use. So retries are set to none, one attempt per request, and the pool is a blocking one of 50 whose wait counts against the timeout below, so a burst waits briefly instead of failing open. A cancelled command closes its connection (redis-py disconnects on any `BaseException` while sending or reading), so a timeout cannot leave a half-read reply on a pooled connection.
  - Each `take` runs under `asyncio.timeout(0.25)`, and the client's own connect and socket timeouts are 0.25 s too. A timeout is `RateLimitUnavailable("timeout")`; a `redis.exceptions.RedisError` (connection refused or lost, a script error, a full pool) or an `OSError` is `RateLimitUnavailable("store_error")`; an unusable reply is `RateLimitUnavailable("bad_reply")`. Any other exception is a bug and gets the usual 500 (D-019).
  - On `RateLimitUnavailable` the request **goes on as if it were allowed**, and one WARNING line goes to `llmgateway.ratelimit`: `ratelimit_unavailable request_id=<id> reason=<timeout|store_error|bad_reply> error=<exception type name>`. Never the Redis URL, a key or an exception message.
  - **Startup:** `LLMGATEWAY_REDIS_URL` is required. Unset or blank, not parseable by `urlsplit` (which, as for `database_url` under D-091, includes a port that is not a number from 0 to 65535), a scheme other than `redis` or `rediss`, or no host stops startup with `llmgateway: configuration error: <message>` naming the variable, never the value. It is read after the database settings. The client connects on first use, so the gateway starts while Redis is down and uses it as soon as it answers. Compose sets it to the `redis` service (D-078), and the api now waits for Redis to be healthy.
- **Why it differs from auth (D-091):** auth decides whether a caller may spend at all; failing open there would give anyone free provider calls. The limiter only shapes how fast a caller that auth has already verified may go. With Redis down, every request is still authenticated, still recorded and still billed to its tenant; what is lost is the rate cap, for the outage's length. Failing closed would turn a Redis outage into a full outage of a gateway whose database and providers are fine, and Redis would become a second single point of failure for no security gain. 250 ms is far above a healthy local round trip and bounds what a hung Redis adds to each request.
- **Alternatives:** Fail closed with 503 (above); fall back to an in-process bucket per worker while Redis is down (a looser limit, N workers times the rate, and a second implementation to test); a longer timeout such as auth's 2 s (adds up to 2 s to every request during an outage).
- **Risk:** During an outage a verified key is unlimited; spend caps, which would bound the cost, are stretch. A hung Redis adds up to 250 ms per request. The line is written once per request, so an outage under load writes one line per request, as auth's does.
- **Revisit when:** A spend cap exists, Redis moves off the local network, or an outage is measured.
- **Amended (2026-11-12, M16's first integration run): the budget is 1 s, not 250 ms.** Every 250 ms above becomes 1 s: the `asyncio.timeout`, the socket and connect timeouts and the pool's wait (`LIMIT_TIMEOUT_SECONDS = 1.0`). D-109's exactness test failed with 250 ms. Reproduced by hand (`scratchpad/repro16.py`, not in the repo) against a second gateway from the image at f0bca7a with a burst of 20 and a refill of 0.001 per second, on this machine on a day when the test suite ran about four times slower than usual: three rounds of 70 concurrent requests, each with a fresh key, let 70, 47 and then 20 through, with 88 `ratelimit_unavailable reason=timeout` lines. The budget is wall time on the one event loop, so on a cold gateway the 70 requests' own work (their auth lookups, 50 new Redis connections at once) used it up before Redis's answer was read, and a cancelled command drops its connection, so the pool stayed cold. The same three rounds with the module's budget set to 1 s (mounted into that container only): 20 and 50 each time, no `ratelimit_unavailable` line. **Risk added:** a gateway so overloaded that one `take` waits more than 1 s fails open for those requests, which is when a limit matters most. A Redis that hangs costs up to 1 s per request. Half of auth's 2 s, and measured to hold under this burst; not measured beyond it.
- **Amended (2026-11-12, M16 review): the Redis URL carries no options.** A `LLMGATEWAY_REDIS_URL` with a query string (anything after `?`, even empty) stops startup with a configuration error naming the variable. redis-py's `from_url` lets query options such as `socket_timeout` or `max_connections` override the client settings above, and a bad option value raised at import with a traceback instead of the configuration error line (D-044). The database number stays in the path (`/0`).
- **Amended (2026-11-12, before M17, the owner's brief): a timeout sheds the request, a breaker decides when Redis is down, and the pool is warmed at startup.** The 1 s amendment moved the threshold but kept the failure mode: a gateway busy enough that one `take` waited past the budget let that request through unlimited, which is when a limit matters most. The two cases are now separate.
  - **A take that times out is shed:** 503, code `rate_limit_timeout`, message "The rate limiter did not answer in time.", `Retry-After: 1`. Like a 429 it stops in the middleware: no provider, no usage record, neutral for every provider breaker. One WARNING line: `ratelimit_shed request_id=<id> reason=timeout error=<exception type name>`. A timeout is the `asyncio.timeout` around the take or redis-py's own socket or connect timeout, `redis.exceptions.TimeoutError`, which is a `RedisError` and so is caught before the store errors. The pool's wait no longer has its own limit (`timeout=None`; in redis-py 8.1.0's `BlockingConnectionPool.get_connection`, `None` means wait until a connection is free), so a full pool is bounded by the take's budget and is a timeout, not a store error.
  - **Redis unreachable fails open, as above:** a store error (connection refused or lost, a script error, any other `RedisError` or an `OSError`) or an unusable reply still lets the request through with the `ratelimit_unavailable` line. These come back at once, so passing the request costs no wait.
  - **The limiter's breaker:** each `RedisRateLimiter` holds one `CircuitBreaker` (D-055's class, in process memory, so one per worker) named `redis:ratelimit`, a name no config instance can have (`:` is not allowed in one, D-044), with `BreakerPolicy(window_size=5, failure_threshold=5, cooldown=5.0)`: five failures in the last five outcomes, that is five in a row, because a success enters the window. A failure is a store error, an unusable reply, or a timeout that counts (next point). A success is any decision, allowed or refused. A cancellation, such as a client that left, is neutral, and so is any other exception, from the call or from the check of its reply, a bug that still gets the usual 500 (D-019), so a probe always gives its slot back and the breaker cannot be wedged half-open. While open, `take` makes no Redis call and the request goes on at once with `ratelimit_unavailable request_id=<id> reason=circuit_open error=CircuitOpen`. 5 s after opening, the next take is the one probe and the others meanwhile pass at once; the probe's outcome closes or reopens it, as D-057 says for providers. State changes write D-059's `breaker_state_change` line with `provider=redis:ratelimit`.
  - **Which timeouts count:** a timed-out take is a failure only if no take of the same limiter succeeded between the moment it started and the moment it timed out; otherwise it is neutral. If Redis answered other takes during the wait, the wait was the gateway's own (a busy event loop or a full pool), not Redis's, and counting it would let an overloaded gateway open the breaker and switch the limit off, the failure mode this amendment removes. When Redis is stopped or hung, nothing succeeds, so the timeouts count. Measured on the stack with the M16 image (2026-11-12, `scratchpad/probe_stop.py`, not in the repo): with Redis stopped, the first take failed with `ConnectionError` and each of the next seven timed out at the budget (1,004 to 1,005 ms); with Redis paused, all eight timed out. So timeouts must count, or a stopped Redis would shed every request. The cost: when an outage starts, takes whose wait overlapped the last good answer are neutral, which delays opening by at most one budget, about 1 s (the review's note).
  - **Pre-warm:** the app's lifespan calls `limiter.warm()` before serving. It loads the script (`SCRIPT LOAD`) and opens all 50 pool connections at once, holding each until all are open, then returns them to the pool, within `WARM_TIMEOUT_SECONDS = 2.0` in all. It never raises and never stops startup. It writes one line: `ratelimit_warm opened=<n> of=50` at INFO when all opened, or at WARNING with ` error=<exception type name>` added when fewer did. With Redis down at startup the pool stays cold, as before.
  - **The budget stays 1 s, re-decided and measured.** Shedding changes what the budget costs. Too short, and a burst sheds requests that were within their limit. Too long, and requests wait during a Redis hang, but only until the breaker opens: after five failures in a row on a worker nobody there waits, and a probe waits once per 5 s. Measured with `scratchpad/measure17.py` (not in the repo): this design mounted into a second gateway from the c588e6b image, burst 20, refill 0.001, one uvicorn worker, a fresh key per round, timing every take. Without pre-warm, the first burst of 70 had a slowest take of 161.5 ms (92.0 ms in a second run), and the first 200 had 232.5 ms. With pre-warm, three rounds each: 70 concurrent, slowest take 13.2 to 23.5 ms; 200, 13.7 to 156.3 ms; 500, 373.5 to 708.9 ms (median 104 to 340 ms). At a 1 s budget all nine rounds let exactly 20 through, with 0 shed and 0 failed open. 250 ms would have shed at 500 concurrent. Not measured beyond 500 concurrent on one worker, or on a slower day such as the first amendment's.
  - **Interface:** the budget, breaker and last-success rule live once in `llmgateway/redisguard.py`, for the limiter and M17's cache (D-114): `RedisGuard(breaker, *, timeout, clock)` with `async call(operation, *, accept)`, raising `GuardOpen`, `GuardTimeout`, `GuardStoreError` or `GuardBadReply` (each with only a class name), and `async warm_pool(client, *, connections, budget, script) -> (opened, error type or None)`. In `ratelimit.py`: `RateLimitTimeout(error_type)`; `RateLimitUnavailable.reason` is `store_error`, `bad_reply` or `circuit_open` (no longer `timeout`); the `RateLimiter` protocol gains `async warm() -> None`; `RedisRateLimiter(client, *, burst, per_second, timeout=LIMIT_TIMEOUT_SECONDS, breaker: CircuitBreaker | None = None, clock=time.monotonic)`, which builds its own breaker when given none; `BREAKER_NAME = "redis:ratelimit"`, `BREAKER_POLICY`, `WARM_TIMEOUT_SECONDS`; `redis_client(url)`'s pool has `timeout=None`, everything else as above.
  - **Alternatives:** keep failing open on a timeout with a longer budget (moves the threshold again); fail closed on every Redis failure (a Redis outage becomes a full outage, the argument above); count every timeout toward the breaker, as the brief's first wording has it (an overloaded gateway with a healthy Redis would open it after five timeouts and switch the limit off for 5 s at a time, the same failure with one more step); shed on store errors too (a store error is immediate and says nothing about load, and a stopped Redis would shed until the breaker opened); blame a timeout on the gateway by measuring event-loop lag (a heuristic with its own tuning, where "did Redis answer anyone meanwhile" is a fact); a breaker per Redis shared with M17's cache (M17 decides).
  - **Risk:** a gateway so busy that no take completes within a whole budget counts its timeouts, opens the breaker and runs without a limit for 5 s at a time; that needs a 1 s stall of the event loop, not measured here. A shed is a 503 for a request that may have been within its limit. Each worker's breaker and last success are its own. During an outage each worker's probe waits up to 1 s and is shed, once per 5 s. Pre-warm holds 50 connections per worker for the process's life.
  - **Proof (extends D-109):** the exactness test still gives exactly 20 through and 50 limited; with Redis stopped, once the breaker's open line is in the log, requests pass, each well under the budget, with `reason=circuit_open`; with Redis paused (`docker compose pause redis`; `DEBUG SLEEP` is refused by default since Redis 7, `enable-debug-command no`), every take made is shed with 503 `rate_limit_timeout` and none passes until the breaker opens.
- **Amended (2026-11-12, during M17): one reconnect on a connection the server closed.** Found on M17's fresh stack: the integration suite run a second time, after the first run's outage tests had restarted Redis under the same gateway, had cache lookups fail with `ConnectionError` and bypass. Reproduced in the api container (`scratchpad/stale.py`, not in the repo): a client pings, Redis restarts, the next command fails with `ConnectionError: Connection closed by server.` and the one after it succeeds. In redis-py 8.1.0 the pool's `ensure_connection` does not notice a connection the server closed while it sat idle; the command is written, the read meets EOF, and with retries at 0 that is an error. The fresh stack measured it (`scratchpad/restart_probe.py`, not in the repo): after a stop and start, the first of 60 sequential opted-in requests bypassed and the other 59 missed; sequential requests reuse one connection, so a concurrent burst meets as many dead connections as it draws. For the limiter each is a request let through unlimited, and five in a row open its breaker for 5 s; so every Redis restart left up to 50 dead connections per worker, each failing once.
  - **The client retries once, on `redis.exceptions.ConnectionError` only:** `retry=Retry(NoBackoff(), 1, supported_errors=(ConnectionError,))` in `redis_client`, and so in `cache_client`, which is the same client (D-114). redis-py disconnects the failed connection before the retry, so the retry connects afresh. A timeout is never retried: it is not in `supported_errors`, and the call's budget bounds the retry anyway, so a take still waits at most 1 s and a lookup 250 ms.
  - **Why:** the failure is the client's, not Redis's: Redis is up and answers the reconnect. A retry inside the client is the fix redis-py offers for it; a health check (`health_check_interval`) sends a PING before a command but, with retries at 0, fails the same way.
  - **Alternatives:** keep no retries (each Redis restart costs up to 50 unlimited requests per worker, or a 5 s open breaker); retry on timeouts too (doubles the wait under load, and the budget would cut it anyway); retry in `RedisGuard` (a second copy of what the client already does, and the guard cannot tell a dead pooled connection from a refused one without reading messages).
  - **Risk:** a connection lost after the script ran and before its reply runs the script twice and takes two tokens: one request refused that would have passed, the strict side. A Redis that refuses connections now costs two fast attempts per take instead of one. CLAUDE.md's "retries happen only in the router" was read here as about provider calls (D-032); the owner confirmed that reading on 2026-11-13 and CLAUDE.md now says "Provider calls are retried only in the router". A provider call is still never retried outside the router.
  - **Proof:** a unit test on the real client against a listener that answers one command and then closes the connection: the next call succeeds; the retry settings are pinned (one retry, `ConnectionError` only); an integration test restarts Redis under the running gateway and then sends a concurrent burst: every opted-in request is a `hit` or `miss`, none `bypass`, and no `ratelimit_unavailable` or `cache_unavailable` line is written after the restart.
- **Confirmed by the owner (2026-11-13):** the last-success rule above stands. A timeout counts toward the limiter's breaker only if no other take succeeded meanwhile; that is what tells an overloaded gateway apart from a Redis that is down. The brief's wider "consecutive store failures or timeouts" is not adopted. The fourth amendment's reading of CLAUDE.md is confirmed too (Risk above).

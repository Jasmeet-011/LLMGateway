# D-119 The load-test stack: Compose overrides, one worker, a load-test config, limits above the test rate, a fresh key per run

- **Decision:** Every run uses the Compose stack (D-078) with `loadtest/compose.loadtest.yaml` added, and for some measurements one more override file. All are committed, so a run's conditions are the files plus the command.
  - **`config/loadtest.toml`**, mocks only, selected by `LLMGATEWAY_CONFIG=/app/config/loadtest.toml` (the image copies `config/`):
    - `mock-steady`: 20 ms, failure rate 0, seed 3. Alias `steady` = [`mock-steady`/`mock-a`]. Measurements 1, 2, 3 and 5.
    - `mock-primary`: 20 ms, failure rate 0.3, `unavailable`, seed 1; `mock-secondary`: 40 ms, failure rate 0, seed 2. The same values as `config/mock-fallback.toml`, which named them measurement 4's. Alias `failures-off` = [`mock-primary`/`mock-a`]; alias `failures-on` = [`mock-primary`/`mock-a`, `mock-secondary`/`mock-b`]. Measurement 4.
    - `mock-outage`: 20 ms, failure rate 0, seed 4. Alias `outage-off` = [`mock-outage`/`mock-a`]; alias `outage-on` = [`mock-outage`/`mock-a`, `mock-secondary`/`mock-b`]. Measurement 8.
  - **One uvicorn worker**, the image's command (no `--workers`), plain uvicorn 0.54.0 with h11 and the asyncio loop (no uvloop, no httptools; neither is a dependency). D-064's fault window and D-055's breakers are per process, so one worker keeps measurement 8's window and breaker single, as D-064's Risk asks.
  - **Limits above the test rate:** `LLMGATEWAY_RATE_LIMIT_BURST=100000` and `LLMGATEWAY_RATE_LIMIT_PER_SECOND=100000` for every measurement but 5, against at most 50 req/s in the paced runs and a closed loop that cannot approach 100,000/s on one worker. The limiter still runs its script on every request, so its cost is in the overhead; it never refuses. Measurement 5 adds `loadtest/compose.burst.yaml`: burst 20, refill 1 per second.
  - **No cache opt-in** except measurement 3: no other script sends `x-gateway-cache: use`, so the cache makes no Redis call and every 200 says `bypass` (D-111, D-116). Measurement 3 opts in on every request.
  - **Key cache:** the default 10 s (D-090), except D-090's second measurement 1 variant, which adds `loadtest/compose.nokeycache.yaml` (`LLMGATEWAY_KEY_CACHE_SECONDS=0`).
  - **Measurement 8's window:** `loadtest/compose.outage.yaml` sets `LLMGATEWAY_FAULTS=mock-outage=1.0@60+30` (D-064): 100% failure from 60 s after the instance's first call, for 30 s. Nothing else sets the variable.
  - **Per run:** `api` (and `direct-mock`) are recreated, so every run starts a fresh process with closed breakers, a fresh mock seed sequence and an empty key cache. Postgres and Redis keep running. A new API key is made for each run, with the run's id as its tenant, so its bucket starts full, its cache entries cannot be another run's (D-110), and its usage rows are found by tenant. The key goes to k6 through the environment, never on a command line or in a file, and the runner fails the run if it finds the key in any saved output.
  - **One runner,** `loadtest/run.ps1 -Run <run id>`, does all of the above from the run id alone (D-121 lists the ids), runs k6, waits 5 s for the usage writer, and saves the run's raw output under `docs/results/raw/<run id>/`: `records.jsonl` (k6's per-request lines), `summary.json` (k6's summary export), `api.log` (the gateway's log lines since the recreate), `usage.tsv` (usage rows per outcome and instance, for measurements 4 and 8), and `run.json` (the run id, the command, the Compose files, the git commit, the api image id, the k6 image, start and end times in UTC).
- **Why:** The overrides keep the committed `compose.yaml` the developer stack while making every load-test setting a reviewed file, not a shell variable typed at run time. Separate aliases on one config let one image serve every measurement. A recreate per run makes the three runs of a measurement independent of each other's breaker state and mock sequence; a key per run does the same for the bucket, the cache and the usage rows.
- **Alternatives:** `--workers 4` (more throughput, but four fault windows, four breakers and four rate-limiter breakers, so measurement 8's timeline would be four overlapping ones; D-064 asks for one worker or a statement); shell variables for the limits and faults (the run's conditions would live only in a terminal); the limiter switched off (it is part of the gateway being measured); `FLUSHALL` between runs (needs Redis's CLI per run and does nothing a fresh tenant does not).
- **Risk:** One worker understates what the gateway does on more cores; measurement 2's number is one worker's. The plain asyncio loop and h11 are slower than uvloop and httptools, and that is the shipped image. Postgres's `usage_records` grows across runs (rows are found by tenant). The stack shares one laptop with k6.
- **Revisit when:** The image changes its server or worker count, or a measurement needs more than one worker.

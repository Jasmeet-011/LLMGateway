# D-121 The run protocol: pre-registered runs in a fixed order, three repetitions, median and range, no quiet reruns

- **Decision:** The runs below are written into RESULTS.md, with their exact commands, and pushed before the first of them starts. Each is `.\loadtest\run.ps1 -Run <id>`; `<r>` is 1, 2 and 3. Paced rates are k6 `constant-arrival-rate` with `timeUnit` 1 s.
  - **Measurement 1:** script `steady.js`, a `warmup` scenario (10 req/s for 10 s, not counted) then `measure` (50 req/s for 60 s, 3,000 requests). Ids `m1-direct-r<r>` (the direct mock), `m1-gateway-r<r>` (alias `steady`, default key cache) and `m1-nokeycache-r<r>` (alias `steady`, key cache 0, D-090's second run).
  - **Measurement 2:** script `throughput.js`, `warmup` (5 virtual users for 10 s, not counted) then `measure`: 50 virtual users in a closed loop for 60 s on alias `steady`. Throughput is successful responses per second of the measured scenario. Id `m2-r<r>`.
  - **Measurement 3:** script `cache.js`, `warmup` (10 req/s for 10 s on alias `steady`, no opt-in, not counted) then `measure` (50 req/s for 60 s, opted in). Workload `hot10-repeat80`: request *i* of `measure` (from `exec.scenario.iterationInTest`, starting at 0) sends a unique prompt when *i* mod 5 = 0 and otherwise hot prompt number *k* mod 10, where *k* = *i* − floor(*i*/5) − 1 counts the other requests from 0, so the ten hot prompts take turns; every prompt carries the run id, so the cache is cold at the start of each run. 80% of requests repeat one of ten prompts; the 20% unique ones, the first sight of each hot prompt, and any repeat that arrives before the first answer is stored (D-115) miss. (Amended before any code: the first wording, hot prompt *i* mod 10, would have used only eight of the ten, since *i* mod 5 ≠ 0 rules out two residues mod 10.) Id `m3-r<r>`.
  - **Measurement 4:** script `failures.js`, one scenario `measure`, 50 req/s for 60 s, no warm-up (it would spend mock rolls and breaker outcomes). Ids `m4-off-r<r>` (alias `failures-off`, A) and `m4-on-r<r>` (alias `failures-on`, B). After each, the accounting cross-check (D-122).
  - **Measurement 5:** script `burst.js` with `compose.burst.yaml` (burst 20, refill 1/s): scenario `burst`, 100 requests from 100 virtual users at once (`shared-iterations`); then scenario `paced` from 40 s, 0.5 req/s for 20 s (10 requests), when the bucket has refilled. Correct behavior: in `burst`, the 200s are at most 20 plus the refill over the burst's length, every other response is 429 with `Retry-After`, and nothing else; in `paced`, every response is 200. Id `m5-r<r>`.
  - **Measurement 8:** script `failures.js` with `compose.outage.yaml`, one scenario `measure`, 50 req/s for 150 s, no warm-up, so the run's first request is `mock-outage`'s first call and the window is 60 s to 90 s of the run. Ids `m8-off-r<r>` (alias `outage-off`) and `m8-on-r<r>` (alias `outage-on`). Breaker thresholds as shipped: 15 failures in the last 20, 30 s cooldown, one probe (D-057).
  - **Measurements 6 and 7** are not run: request coalescing and spend caps are stretch and not built (D-031). RESULTS.md says so.
  - **Order:** m1 (direct, gateway, nokeycache) for r1, then r2, then r3; m2 r1 to r3; m3 r1 to r3; m4 (off, on) for r1, r2, r3; m5 r1 to r3; m8 (off, on) for r1, r2, r3. Alternating variants within a repetition keeps slow drift out of the comparisons.
  - **Reporting:** every run's numbers go in RESULTS.md. A measurement's figure is the median of its three runs, with the minimum and maximum beside it, never the best run.
  - **Reruns:** a run is repeated only when a defect is found in the tooling or the stack, recorded in PROGRESS.md's mistakes log, and the rerun is labeled `<id>-rerun<k>`; the first run's output and numbers stay in RESULTS.md, marked with the defect. A run whose numbers look wrong is not rerun for that reason.
  - **Smoke runs:** before the pre-registered runs, short runs (`smoke-*` ids, a few seconds at a few requests per second) check that the scripts and the runner work. They are listed in RESULTS.md with their purpose; their numbers are not results.
- **Why:** PLAN.md fixes the measurements so results cannot be cherry-picked; fixing the runs, their order and their aggregation before running extends that to the choices PLAN.md left open. The median of three is robust to one odd run, and the range shows the spread. 50 req/s is chosen before any measurement as a load that one worker should carry well below saturation, so the overhead is not queueing; measurement 2 then shows how far below it is. If it is not below, that is a result.
- **Alternatives:** The rate as a fraction of measurement 2's throughput (more meaningful, but the commands could not be written before the first run, as the owner asked); more than three runs (more time, same method; three is the owner's minimum); reporting the mean (one bad run moves it); a fixed-duration burst instead of `shared-iterations` (a burst of known size is what the 429 count is checked against).
- **Risk:** 50 req/s is a modest rate and the resume bullet will say so (superseded by D-123: the owner's final bullet does not state the rate; RESULTS.md and PLAN.md's trace lines do). Three runs give a range, not a confidence interval. A defect found halfway means some runs are reruns and RESULTS.md has to show both.
- **Revisit when:** The owner wants another rate or more repetitions; that is a new, labeled set of runs, never a replacement.

  - **Guard in `run.ps1`:** before anything else it reads the System log's latest Kernel-Power 506 or 507 event and refuses to start when it is a 506 (the machine is in standby). From then until it finishes, it holds a power request, `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)`, released in a `finally`, so the display's idle timeout, the usual way into standby, does not fire during a run. A closed lid or the power button still sends the machine to standby, so after the run it lists every Kernel-Power 506 and 507 event between the run's start and end in run.json as `power_events` (each `{"utc", "id"}`), and if there is any, it saves the run's output and then stops with an error, so a driver stops at that run and the run is recorded as disturbed.
  - **Reporting:** the first pass's 30 runs keep their output, and their figures stay in RESULTS.md beside the reruns', from `tables-first-pass.md` (D-122, amended).

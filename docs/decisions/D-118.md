# D-118 k6 2.3.0 in a container, pinned by index digest, on the Compose network

- **Decision:** Settles PLAN.md M18's "the k6 version". The load generator is the `grafana/k6` image at `2.3.0@sha256:2dd4756ec6e14e62778916e1eb850108e4b499304c02df56760fa0bdb0fba0b8`, the multi-platform index (linux/amd64 manifest `sha256:7637f6a2c358cf1decd8b1f339649da429f5e91901ecee19bfc0486c9edb5b13`), `k6 version` printing `k6 v2.3.0 (commit/e088784614, go1.27.1, linux/amd64)`. Docker Hub's API on 2026-11-13 gave its last push as 2026-10-24, 20 days earlier. It runs as a `k6` service in `loadtest/compose.loadtest.yaml`, on the Compose network, and reaches the gateway at `http://api:8000` and the direct mock (D-120) at `http://direct-mock:8000`. The scripts are in `loadtest/k6/`. No k6 binary is installed on the host and no port is used from the host.
  - What the scripts rely on, each seen working on this image on 2026-11-13 with a probe script (`scratchpad/k6probe`, not in the repo): `constant-arrival-rate`, `constant-vus` and `shared-iterations` executors with `startTime`; `k6/execution`'s `exec.scenario.name` and `exec.scenario.iterationInTest`; `res.timings.duration`; `--summary-export`; `--console-output` with `--log-format json`, which writes one JSON object per `console.log` call with the logged string in `msg`.
- **Why:** 2.3.0 is the newest release under D-029's floor as D-079 applies it to images: 2.4.0 and 1.8.3 were both pushed on 2026-11-12 and 13. Running k6 in the Compose network keeps Docker Desktop's host port forwarding out of every latency, and the gateway and the direct mock are reached the same way, which measurement 1's difference depends on.
- **Alternatives:** The 1.x line (1.8.2, pushed 2026-10-24, also under the floor; 2.x is the current major and nothing here needs 1.x); a k6 binary on Windows (no digest to pin, and its requests would cross the host's port forwarding); `--out json` for per-request data (every metric sample, about fifteen lines per request); `hey` or `wrk` (PLAN.md and the resume bullet name k6).
- **Risk:** k6 shares the Docker VM's CPUs with the gateway, so a saturated k6 would inflate every latency; the summary's `dropped_iterations` and k6's own CPU are the signals, and RESULTS.md lists it as a limitation. A deleted digest breaks the runs loudly.
- **Revisit when:** A new k6 release is past the floor and needed, or the load moves off this machine.

# D-122 Analysis: `lgwload`, standard library only; the accounting cross-check; measurement 8's chart

- **Decision:** The numbers in RESULTS.md come from `loadtest/report.py`, which reads only `docs/results/raw/` and writes `docs/results/summary.json`, `docs/results/tables.md` and `docs/results/m8-outage.svg`. Its logic is the package `loadtest/lgwload/` (standard library only; type-checked by mypy and tested like the rest). `report.py` is re-run after the last run; its outputs are committed with the raw files they came from.
  - **Records** (`lgwload.records`): `parse_records(lines) -> list[Record]` reads k6's `--log-format json` console output: each non-blank line is a JSON object whose `msg` is a JSON object with `sc` (scenario, a non-empty string), `t` (start, integer epoch milliseconds, >= 0), `s` (HTTP status, integer 0 to 599, 0 for a transport error), `d` (duration in ms, a number >= 0), `ok` (boolean), and optionally `c` (the `x-gateway-cache` header), `i` (`provider_instance`) and `ra` (`Retry-After`), each a string or null. `Record` is a frozen dataclass with `scenario`, `start_ms`, `status`, `duration_ms`, `ok`, `cache`, `instance`, `retry_after`. A line that is not valid JSON, has no string `msg`, or whose record breaks any rule raises `ValueError` naming the line's number, counting from 1; nothing is skipped silently. A boolean is not a number here.
  - **Statistics** (`lgwload.stats`): `percentile(values, q)`, nearest rank: the smallest value such that at least `q` percent of the values are at most it, that is the value at position `ceil(q/100 * n)` counting from 1 in sorted order, for `0 < q <= 100`; an empty input or a `q` outside that range raises `ValueError`. `median(values)`: the middle value, or the mean of the two middle values for an even count; empty raises `ValueError`. `spread(values) -> Spread(median, low, high)`.
  - **Measures** (`lgwload.measures`): `latency(records, scenario) -> Latency(count, failed, p50, p95, p99)` over the successful records of that scenario (`failed` counts the others; no successful record raises `ValueError`); `success(records, scenario) -> Success(succeeded, total)` with `rate` = succeeded / total; `overhead(gateway, direct) -> dict[str, Overhead]`, where both arguments map a repetition number to a `Latency`, the keys must be equal and non-empty (else `ValueError`), and for each of `p50`, `p95`, `p99` the `Overhead` holds the per-repetition differences in repetition order and their `Spread`; `per_second(records, scenario) -> list[Second(second, sent, succeeded)]`, bucketing each record of the scenario by `floor((start_ms - origin) / 1000)` with `origin` the scenario's earliest `start_ms`, every second from 0 to the last present, empty seconds included as `sent=0`; `cache_split(records, scenario) -> CacheSplit(hits, misses, other, total, hit_rate, hit, miss)` where `hit` and `miss` are the `Latency` of the successful records with `cache` `"hit"` and `"miss"` (None when there are none), `other` counts the rest, and `hit_rate = hits / total`.
  - **Gateway log** (`lgwload.gatewaylog`): `breaker_events(lines) -> list[BreakerEvent(ts_ms, provider, from_state, to_state, reason)]` from every line containing `breaker_state_change `, with D-059's fields and D-082's `ts` (ISO 8601 UTC with `+00:00`), converted to epoch milliseconds; a breaker line missing a field or with a bad `ts` raises `ValueError` naming the line. `gateway_counts(lines, tenant) -> GatewayCounts(by_status, failed_attempts, fallbacks)`: `by_status` counts request lines (D-026's `request_id=<id> tenant=<tenant> ... status=<n> ...`) of that tenant by status; `failed_attempts` and `fallbacks` count `attempt_failed` and `fallback_taken` lines whose `request_id` is one of that tenant's request lines. Other lines are ignored.
  - **Usage** (`lgwload.accounting`): `parse_usage(lines) -> UsageCounts(success, failed, abandoned, by_instance)` from `usage.tsv`, one row per line, `outcome<TAB>provider_instance<TAB>count`, outcome one of `success`, `failed`, `abandoned`, count a non-negative integer; anything else raises `ValueError` naming the line. `cross_check(k6_succeeded, gateway, usage) -> list[str]`, empty when everything agrees, otherwise one plain sentence per disagreement: usage `success` rows equal the gateway's 200 lines and k6's successes; usage `failed` rows equal the gateway's `attempt_failed` lines; there are no `abandoned` rows (no request is streamed or cancelled). One usage row per adapter attempt (D-095) means total rows = successful attempts + failed attempts.
  - **Chart** (`lgwload.chart`): `outage_svg(runs, window_start_s, window_length_s) -> str`, a self-contained SVG (no script, no external reference) plotting each run's success rate per second (succeeded / sent, a gap where sent is 0) against seconds since the run's first request, fallback-on runs in one color and fallback-off runs in another, the fault window shaded, and each breaker state change as a marker labeled with its new state; the same input gives the same bytes.
  - **Amended (2026-11-13, after the first smoke run, before any measured run): k6's own messages.** The first smoke run printed `{"level":"warning","msg":"\"cli\" level configuration overrode scenarios configuration entirely"}`. The builder first read it as a line of the `--console-output` file and amended `parse_records` for that; it was k6's own log on stderr, which `run.ps1` printed and did not save (corrected the same hour; mistakes log). So:
    - `run.ps1` saves k6's stderr with its stdout in `k6.txt`, so k6's own warnings (such as a paced scenario running short of virtual users) are kept with the run.
    - `parse_records` reads as records only lines whose `level` is `"info"` (what `console.log` writes), with every rule above. A line with any other string `level` is skipped by it (a script's `console.warn` or `console.error` would write one), and a line with no string `level` is an error like any other bad line. `k6_messages(lines) -> list[str]` returns the `msg` of every non-`info` line of the records file, in order, under the same JSON rules.
    - `k6_log_messages(lines) -> list[str]` reads `k6.txt`: every line that parses as a JSON object with a string `level` other than `"info"` and a string `msg` gives that `msg`, in order; every other line (k6's text summary, Compose's container messages, an `info` line) is ignored, since that file is a mix by design.
    - The report lists both per run, so k6's warnings are shown, never dropped quietly.
  - **Amended (2026-11-13, after the first pass): requests refused before auth, the first pass's figures, power events.**
    - `GatewayCounts` gains `before_auth: dict[int, int]`, with an empty default: request lines whose tenant is `-` and whose status is not 200, counted by status, whatever the `tenant` argument. Such a line is a request the gateway answered before it knew the key's tenant (401, or 503 `auth_unavailable`, D-091). A tenant-less 200 is a health check, since a chat request cannot succeed without a tenant, so those are left out. `run.ps1` recreates `api` for every run, so every line in a run's `api.log` belongs to that run. The first pass showed why: m4-on-r3's 14 `503 auth_unavailable` were in no column, and its table said "200: 2985" beside 2,999 requests.
    - The report computes `before_auth` for every run whose catalog target is `api`. The measurement 4 and 8 tables show it in a column "Refused before auth" (`-` when empty), and `tables.md` has a section "Requests refused before auth" listing every run whose count is not empty, or `- none`. (Corrected the same hour, before any test: the first wording said `tables.md` "ends with" this section, which the power-events section below and the smoke-run list contradict.)
    - `build(repo, first_pass=False)`: with `first_pass=True`, every catalog run uses its first output directory `<id>`, even when it has reruns, and its `used` is that id. When any catalog run has a rerun, `main` also writes `docs/results/summary-first-pass.json`, `docs/results/tables-first-pass.md` (titled as the first pass, including the runs that reruns replaced) and `docs/results/m8-outage-first-pass.svg` from it. When no run has a rerun, it writes only the three usual files. In every table a row is labeled with the output directory it uses: `<id>-rerun<k> (replaced: <id>)` in `tables.md`, and `<id> (replaced by: <id>-rerun<k>)` in `tables-first-pass.md`.
    - Each run's summary holds `power_events` from its run.json: the list as written, or `null` when run.json has no such field (runs made before the D-121 guard). `tables.md` has a section "Power events during a run" listing every run whose list is not empty, or `- none`. (Corrected after the M18 review, round 1: a run whose `power_events` is `null` is listed in that section as `- <run>: not recorded (made before the D-121 guard)`, never folded into `- none`. The first wording printed `- none` for the first pass, 27 of whose runs ran in standby. `- none` now appears only when every run's list is recorded and empty.)
  - **Accounting run:** `run.ps1` writes `usage.tsv` after measurements 4 and 8 with one parameterized query through `psql`'s `\bind` (`SELECT outcome, provider_instance, count(*) FROM usage_records WHERE tenant_id = $1 GROUP BY 1, 2 ORDER BY 1, 2`), never with the tenant pasted into the SQL (CLAUDE.md).
- **Why:** Computing every figure from committed raw output with committed, tested code means anyone can regenerate the tables and the chart, and a transcription error in RESULTS.md shows against `tables.md`. The standard library is enough for percentiles and an SVG, and PLAN.md allows no dependency for M18. Nearest rank never invents a value between two measured ones. Strict parsing makes a truncated or corrupted record file fail the report instead of quietly shrinking a run.
- **Alternatives:** k6's own summary percentiles (its trend algorithm is not documented here, unverified; the summary is still saved for comparison); matplotlib for the chart (a new dependency); a notebook (not testable by `check.ps1`); interpolated percentiles (a value no request had).
- **Risk:** The SVG is plain; its correctness is tested on structure, not on how it looks. The cross-check counts rows and lines; it does not compare token counts, which the mock fakes (D-016).
- **Revisit when:** A measurement needs streaming records or more than the counts above.

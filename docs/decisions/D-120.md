# D-120 Definitions: a successful response, latency, gateway overhead, and measurement 4's A and B

- **Decision:** Fixed before any run; RESULTS.md states each in plain words.
  - **Successful response:** HTTP 200 whose body is JSON with a string `content`, checked in the k6 script (`ok` in each record). Anything else is not a success: a 4xx or 5xx, a body that does not parse, a k6 transport error (status 0), or k6's 120 s request timeout, which is above the router's 90 s deadline (D-061) so that the gateway always answers first. Every request is non-streaming.
  - **Success rate:** successful responses divided by requests k6 started in the measured scenario. k6's `dropped_iterations` (requests a paced scenario could not start) are reported next to it, not hidden.
  - **Latency:** k6's `res.timings.duration` for one request: sending, waiting and receiving, without connection setup (k6 keeps connections alive per virtual user). Percentiles are nearest-rank over the successful responses of the measured scenario. Failed requests are counted, not timed.
  - **Gateway overhead (measurement 1):** what the gateway adds over calling the same mock directly. "Directly" is `loadtest/direct_mock.py`: a Starlette app with one `MockProvider(latency_ms=20)`, the same object and latency as `mock-steady`, served by the same uvicorn, single worker, from the same image, in a container beside the api, on `POST /v1/chat`. It reads the body and discards it, calls `complete` on one fixed request, and returns the result as JSON. So its latency is the mock's 20 ms sleep plus a minimal HTTP round trip, and the gateway's extra is everything the gateway does: auth, the body limit, the rate limiter's Redis script, parsing and validation, routing, the usage record, logging and the response. The mock's latency is subtracted by this difference, not by subtracting 20 ms: both sides pay the same sleep. For repetition *i*, overhead p*q* = p*q*(gateway run *i*) − p*q*(direct run *i*), for *q* in 50, 95 and 99, with the two runs made back to back; the reported figure is the median of the three repetitions, with their minimum and maximum. This is a difference of percentiles, not a percentile of per-request differences, because one request cannot go both ways.
  - **Measurement 4's A and B:** A is the success rate with fallback off: alias `failures-off`, the one entry `mock-primary` at 30% injected `unavailable` failures. B is the same load with everything on: alias `failures-on`, `mock-primary` then `mock-secondary`. **In both runs the router's retries, per-attempt and total timeouts and the circuit breaker are on**, because they are code defaults with no switch (D-050: "The values are code defaults, not TOML config"), and adding one would contradict D-050. So B − A is what fallback adds on top of retries, not what the whole reliability layer adds over a bare call. `mock-secondary` injects no failures, so B models one provider failing while the other is healthy. X is 30, the failure rate of each attempt on `mock-primary`; N is the paced rate, 50 req/s.
  - **Hit rate (measurement 3):** responses with `x-gateway-cache: hit` divided by requests in the measured scenario; hit and miss latencies are split by that header.
- **Why:** A success that only checks the status would count a 200 with a broken body. A direct baseline served the same way removes the mock's sleep, the HTTP stack, the Docker network and k6 itself from the overhead at once; subtracting the configured 20 ms would charge the gateway for uvicorn's and k6's time and for `asyncio.sleep`'s lateness. Reading the body and answering a fixed request keeps the baseline minimal, so validation counts against the gateway, the conservative side. Stating that retries stay on in A keeps the resume bullet from implying a bare-call baseline that was never run.
- **Alternatives:** Overhead as gateway latency minus 20 ms (above); overhead from the gateway's own `latency_ms` log field minus the provider's time (the provider's time per attempt is not logged, and it would leave out uvicorn's parsing and the network); a direct baseline that validates the body as `ChatRequest` (would move validation out of the overhead); A with retries off through a new setting (contradicts D-050, a stop condition; the owner can amend D-050 for it); A as k6 calling the direct mock at 30% failures (a different measurement from PLAN.md's "with fallback and without fallback"; not run).
- **Risk:** Percentiles of 3,000 requests have their own noise, especially p99, so a difference of two p99s is the noisiest figure here. Back-to-back runs share drift but not every condition. B near 100% says more about the healthy secondary than about the gateway.
- **Revisit when:** The owner wants a bare-call baseline (needs a D-050 amendment), or overhead must be measured per request.
